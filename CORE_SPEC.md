# BigCalc Core Specification

**Файл:** `CORE_SPEC.md`  
**Статус:** Draft 2 — core decisions resolved  
**Назначение:** техническая спецификация математического ядра BigCalc.  
**Область:** только математическое ядро. UI, конкретные калькуляторы-надстройки, `floatX`, конвертер единиц, системы счисления и другие плагины описываются отдельно.

---

## 1. Цели ядра

BigCalc строится вокруг самостоятельного математического ядра, которое:

1. вычисляет вещественные математические выражения;
2. сохраняет точные значения там, где они рациональны и ядро умеет получить их точно;
3. для остальных вещественных значений использует ленивые вычисления;
4. хранит доказанную оценку ошибки в форме ball arithmetic;
5. вычисляет только ту точность, которая фактически нужна потребителю результата;
6. умеет продолжать ранее начатое вычисление, а не обязательно запускать его заново;
7. предоставляет будущим калькуляторам и другим надстройкам стабильный API;
8. не зависит публичными типами от конкретных сторонних математических библиотек.

BigCalc не должен быть привязан к JavaScript `number` как к основной числовой модели.

---

## 2. Не-цели

В текущую версию ядра **не входят**:

- комплексные числа;
- символьная алгебра общего назначения;
- CAS-преобразования;
- специальное символьное хранение `sqrt(2)`, `π/2`, `sin(π)` и аналогичных выражений;
- `NaN`;
- `Infinity`;
- `-Infinity`;
- отрицательный ноль;
- полноценная ветка представления экстремально больших чисел;
- прикладные калькуляторы и их UI;
- миграции старых форматов сохранённых данных.

Для недопустимых математических операций ядро возвращает типизированную ошибку, а не специальное числовое значение.

---

## 3. Общая модель вычисления

Базовый поток:

```text
source text
    ↓
input normalization
    ↓
tokenizer
    ↓
parser
    ↓
immutable AST
    ↓
evaluation graph
    ↓
Rational / LazyReal
    ↓
verified approximation
    ↓
verified decimal digits
```

AST описывает структуру выражения.

Evaluation graph описывает вычисляемые значения и их зависимости. Каждый ленивый узел графа имеет собственное состояние вычисления.

---

## 4. Числовые типы

На первом этапе ядро использует два принципиальных класса вещественных значений:

```text
RealValue
├─ Rational
└─ LazyReal
```

Целое число является частным случаем `Rational`.

### 4.1. Rational

`Rational` хранит точное рациональное число:

\[
x = \frac{p}{q}
\]

где:

- `p` — произвольное целое;
- `q` — положительное произвольное целое;
- `gcd(|p|, q) = 1`.

Инварианты:

```text
denominator > 0
gcd(abs(numerator), denominator) = 1
```

Примеры нормализации:

```text
6/8    → 3/4
1/-2   → -1/2
-1/-2  → 1/2
0/n    → 0/1
```

Рациональное значение не должно автоматически превращаться в приближённое десятичное число.

### 4.2. LazyReal

`LazyReal` представляет вещественное значение, которое ядро не хранит как точную рациональную дробь.

Примеры:

```text
π
e
sqrt(2)
sin(1)
ln(2)
Gamma(1/2)
```

`LazyReal`:

- хранит собственное состояние вычислительного алгоритма;
- хранит уже достигнутую точность;
- хранит или умеет получить доказанную границу ошибки;
- может запрашивать дополнительную точность своих операндов;
- при повторном запросе большей точности продолжает существующее вычисление, если используемый алгоритм допускает продолжение;
- не обязан хранить символическую форму математического результата.

---

## 5. Точные fast paths

BigCalc не является CAS, но операции должны использовать дешёвые локальные проверки, позволяющие сохранить точность.

Примеры допустимых оптимизаций:

```text
(4/9)^(1/2) → 2/3
2^10        → 1024
10^0        → 1
0+x         → x
x*1         → x
x*0         → 0
```

Допустимы точные специальные случаи функций, если они определяются локально и не требуют общей символьной алгебры.

Fast path не должен превращаться в общий механизм переписывания произвольных выражений.

### 5.1. Exact rational preservation

Если операция над рациональными аргументами имеет рациональный результат и соответствующий exact path реализован, результат остаётся `Rational`.

Например:

```text
1/3 + 1/6 → 1/2
(2/3)^5   → 32/243
```

Если результат нельзя или нецелесообразно получить локальным exact path, вычисление переходит в `LazyReal`.

## 6. Внутренний arbitrary-precision float

Приближённая арифметика ядра использует внутренний конечный arbitrary-precision binary floating-point тип.

Концептуально:

```ts
interface InternalFloat {
    sign: -1 | 0 | 1;
    significand: bigint;
    exponent: bigint;
    precisionBits: number;
}
```

Математический смысл ненулевого значения:

\[
x = sign \cdot significand \cdot 2^{exponent}.
\]

Точное физическое представление может отличаться в зависимости от backend, но публичная семантика должна быть эквивалентна.

### 6.1. Требования

- точность мантиссы динамическая;
- экспонента не должна быть ограничена диапазоном JavaScript `number`;
- ноль имеет единственное каноническое представление;
- `NaN`, бесконечности и отрицательный ноль не являются допустимыми `InternalFloat`;
- `precisionBits` характеризует конкретное приближение, а не математическое значение.

### 6.2. Backend isolation

Конкретный arbitrary-precision backend находится за адаптером:

```text
BigCalc core types
        ↓
BigFloatBackend
        ↓
MPFR/WASM/other library
```

Типы сторонней библиотеки не пересекают публичную границу ядра.

---

## 7. Ball arithmetic

Все неточные вещественные приближения используют модель:

\[
x = c \pm r,
\]

где:

- `c` — центр;
- `r >= 0` — доказанная абсолютная граница ошибки;
- истинное математическое значение обязано находиться внутри `[c-r, c+r]`.

Абстрактно:

```ts
interface Ball {
    center: InternalFloat;
    radius: InternalFloat;
}
```

### 7.1. Инварианты

```text
radius >= 0
center is finite
radius is finite
trueValue ∈ [center - radius, center + radius]
```

Радиус — настоящее числовое значение, а не «количество правильных цифр».

### 7.2. Rational → Ball

`Rational` остаётся точным источником истины.

Если `LazyReal`-операции требуется приближение рационального аргумента, `Rational` временно преобразуется в ball с требуемой точностью и доказанной границей ошибки.

---

## 8. Directed/outward rounding

Любая операция над приближёнными значениями обязана вернуть ball, который гарантированно содержит истинный результат с учётом:

- ошибок входных ball;
- ошибок внутренних вычислений;
- ошибок округления backend.

### 8.1. Эталонная interval-семантика

Эталонная безопасная модель использует interval:

\[
[L,U].
\]

Нижняя граница вычисляется с округлением к `-∞`, верхняя — с округлением к `+∞`.

После этого interval может быть преобразован обратно в:

\[
c=\frac{L+U}{2},
\qquad
r=\frac{U-L}{2},
\]

с дополнительным outward widening, если округление `c` или `r` этого требует.

### 8.2. Минимальные rounding modes backend

Backend должен поддерживать как минимум:

```ts
type RoundingMode =
    | "nearest"
    | "towardNegativeInfinity"
    | "towardPositiveInfinity";
```

Дополнительные режимы разрешены.

### 8.3. Базовые операции

Для:

\[
x\in[L_x,U_x], \qquad y\in[L_y,U_y]
\]

сложение:

\[
L=\operatorname{down}(L_x+L_y),
\qquad
U=\operatorname{up}(U_x+U_y).
\]

Вычитание:

\[
L=\operatorname{down}(L_x-U_y),
\qquad
U=\operatorname{up}(U_x-L_y).
\]

Умножение строится по минимуму и максимуму четырёх произведений границ с outward rounding.

Деление разрешено только после доказательства:

\[
0
otin[L_y,U_y].
\]

### 8.4. Функции

Для монотонной на всём входном interval функции допускается вычисление по границам с directed rounding.

Для немонотонных функций, например `sin` и `cos`, реализация обязана учитывать внутренние экстремумы interval, а не только значения на концах.

### 8.5. Прямые ball-формулы

Реализация не обязана физически строить interval для каждой операции.

Разрешены доказанные прямые ball-формулы, если итоговый ball гарантированно покрывает результат эталонной outward interval-семантики.

### 8.6. Требование к библиотекам

Backend, который не предоставляет directed rounding или эквивалентной доказанной error bound, не может быть единственным источником verified digits.

Такая библиотека может использоваться для эвристик, предварительных приближений или выбора алгоритма, но не для финального доказательства корректности цифр без дополнительной строгой оценки ошибки.

---

## 9. Lazy precision

Пользователь не задаёт числовую точность вычислений вручную.

Потребитель результата формулирует требование:

> доказать `N` значащих десятичных цифр результата.

Операция сама определяет, какая точность требуется от её операндов.

Упрощённо:

```text
parent needs N verified digits
        ↓
parent estimates operand requirements
        ↓
children refine themselves
        ↓
parent recomputes its ball
        ↓
if N digits are not yet proven:
    request more precision
```

Фиксированное правило вида «для результата в N цифр всегда вычислять все аргументы в N+K цифр» не считается достаточной архитектурой.

---

## 10. Propagation требований к точности

Каждый вычислительный узел отвечает за собственную стратегию уточнения.

Например:

```text
AddNode
SubNode
MulNode
DivNode
PowNode
SinNode
LogNode
...
```

могут требовать различную дополнительную точность операндов.

### 10.1. Сложение и вычитание

Для `+` и `-` ядро автоматически увеличивает точность операндов, если cancellation не позволяет доказать необходимые цифры результата.

### 10.2. Остальные операции

Умножение, деление, степень, функции и будущие операции также обязаны распространять error bounds и при необходимости запрашивать уточнение аргументов.

---

## 11. Неопределённость области определения

Если текущая точность аргумента недостаточна, чтобы доказать допустимость операции, операция должна потребовать дополнительную точность.

Пример:

```text
1 / x
```

при:

\[
x = 0.001 \pm 0.01
\]

не может немедленно возвращать результат или ошибку деления на ноль.

Алгоритм:

```text
ball пересекает запрещённую область
    ↓
запросить уточнение аргумента
    ↓
доказана допустимость → вычислять
доказана недопустимость → typed error
достигнут soft time limit → pause
```

То же правило применяется, где релевантно, к `/`, `ln`, `log`, дробным степеням, `Gamma`/факториалу, `tan` и другим функциям с ограниченной вещественной областью определения.

---

## 12. Точный и округлённый ноль

Ядро обязано различать:

```text
ExactZero
RoundedZero
```

`ExactZero` — математически доказанный `Rational(0)`.

`RoundedZero` — значение, чей отображаемый центр стал нулём вследствие precision cutoff.

Округлённый ноль не является доказательством математического равенства нулю. Его ненулевая неопределённость сохраняется в ball и участвует во всех следующих операциях.

---

## 13. Precision cutoff: 3000/3001

Специальный precision cutoff применяется только:

- к сложению;
- к вычитанию;
- к функциям, работающим в градусном режиме, когда это предусмотрено конкретной функцией.

Он не является глобальным пределом точности всего ядра.

### 13.1. Случай ведущей цифры до запятой

Пусть первая ненулевая цифра результата находится в разряде `10^k`, где `k >= 0`.

Тогда сохраняются 3000 цифр после ведущей цифры.

Шаг округления:

\[
q = 10^{k-3000}.
\]

Разряд `10^(k-3001)` является следующим контролируемым разрядом и участвует в округлении.

### 13.2. Случай ведущей цифры после запятой

Если:

\[
0<|x|<1,
\]

глубина не зависит от позиции первой ненулевой цифры.

Сохраняются максимум 3000 десятичных позиций после разделителя.

Шаг округления:

\[
q = 10^{-3000}.
\]

Разряд `10^-3001` используется для округления.

### 13.3. Правило округления

Используется:

```text
round half away from zero
```

То есть:

```text
 1,5 →  2
 2,5 →  3
-1,5 → -2
```

Перенос округления разрешён через любое количество разрядов и через десятичный разделитель.

### 13.4. Математическая модель

После определения шага `q` целевое округлённое значение:

\[
y = q\cdot \operatorname{roundHalfAwayFromZero}\left(\frac{x}{q}\right).
\]

Операция не должна реализовывать это через ненадёжное преобразование результата в строку.

### 13.5. Неоднозначность на границе округления

Поскольку входом является ball, ядро должно refine исходное значение, пока может однозначно доказать округлённый результат.

Если допустимый cutoff уже достигнут, а ball всё ещё пересекает границу между двумя округлёнными значениями, ядро не выбирает сторону произвольно.

Итоговый ball расширяется так, чтобы покрыть оба возможных округлённых результата.

### 13.6. Погрешность cutoff

Для однозначного обычного округления максимальная новая ошибка округления равна `q/2`.

Итоговый radius должен покрывать как минимум эту ошибку, а также всю предыдущую неопределённость, если она требует более широкого ball.

### 13.7. RoundedZero

Если после cutoff округлённый центр равен нулю, но математический ноль не был доказан exact path, результат получает семантику `RoundedZero`.

Пример:

\[
4\cdot10^{-3001}\rightarrow 0.
\]

Если 3001-й разряд вызывает перенос, результат может округлиться не к нулю, а к `10^-3000` по модулю.

### 13.8. Распространение

Precision cutoff непосредственно применяется только в указанных операциях, но созданная им погрешность дальше распространяется через любые операции обычными правилами ball arithmetic.

## 14. Режим углов

В настройках существует глобальный режим:

```text
radians
degrees
```

Он влияет на все функции ядра, для которых аргумент является углом.

### 14.1. Exact degree fast paths

В градусном режиме ядро должно использовать точные fast paths для рациональных специальных углов, когда результат можно установить локально.

Примеры:

```text
sin(0)   → 0
sin(180) → 0
sin(360) → 0
cos(0)   → 1
cos(180) → -1
```

В degree mode число `180` означает 180 градусов; отдельный символ `°` в математическом выражении не требуется.

Такие случаи не должны намеренно вычисляться через приближённое значение `π`, если точный результат можно установить непосредственно по рациональному градусному аргументу.

---

## 15. Алгоритмы математических функций

Для `π`, `e`, `sin`, `cos`, `tan`, `exp`, `log`, `ln`, `Gamma` и других неточных значений ядро не требует конкретного семейства алгоритмов.

Разрешены ряды, argument/range reduction, AGM, алгоритмы Чудновских, бинарное расщепление, другие доказуемо корректные методы и сторонние библиотеки через адаптер.

Обязательные свойства алгоритма:

1. предоставляет доказанную границу ошибки;
2. интегрируется с lazy precision;
3. по возможности сохраняет состояние и продолжает вычисление;
4. поддерживает cooperative cancellation/resource checkpoints;
5. внутренние типы не становятся частью публичного API.

---

## 16. Встроенные константы

Первая версия ядра содержит:

```text
π
e
```

`π` вводится именно символом `π`. ASCII-алиас `pi` в текущую grammar не входит.

Обе константы создают ленивые вещественные значения и вычисляются по мере запроса точности.

---

## 17. Факториал

Оператор `!` является postfix-оператором.

### 17.1. Integer factorial mode

Если Gamma-режим выключен, `x!` разрешён только для целых неотрицательных `x`.

### 17.2. Gamma factorial mode

Если Gamma-режим включён:

\[
x! = \Gamma(x+1)
\]

для вещественных `x`, где правая часть определена в вещественной области.

Отрицательные целые точки-полюса запрещены.

```text
(-1)! → DomainError
```

Комплексное продолжение Gamma не поддерживается.

---

## 18. Итерации функций

Поддерживается синтаксис:

```text
sin[2](x)
```

Показатель итерации — целое `n >= 0`.

```text
f[0](x) = x
f[1](x) = f(x)
f[2](x) = f(f(x))
```

Отрицательные и дробные итерации в текущую спецификацию не входят.

---

## 19. Логарифмы

Поддерживаются:

```text
ln(x)
log(x)
log2(x)
log{2+3}(x)
```

Семантика:

```text
ln(x)  = logarithm base e
log(x) = logarithm base 10
```

### 19.1. Простое основание

Если основание является числовым литералом, допускается компактная форма:

```text
log2(x)
log10(x)
log1,5(x)
```

### 19.2. Основание-выражение

Для произвольного выражения используется:

```text
log{expression}(x)
```

Примеры:

```text
log{2+3}(125)
log{2^3-3}(125)
log{sin(1)+2}(x)
```

Внутри `{...}` допускается полноценное математическое выражение BigCalc.

### 19.3. Совмещение с итерацией

```text
log{2+3}[3](x)
```

означает тройную композицию логарифма с основанием 5.

### 19.4. Grammar

Концептуально:

```text
LogCall :=
    "log" Base? Iteration? "(" Expression ")"

Base :=
      NumberLiteral
    | "{" Expression "}"

Iteration :=
    "[" NonNegativeInteger "]"
```

`log` без `Base` использует основание 10.

### 19.5. Domain

Для вещественного логарифма необходимо доказать:

\[
x>0,\qquad b>0,\qquad b
e1.
\]

Если текущие ball основания или аргумента не позволяют это доказать, узел запрашивает refinement.

---

## 20. Операторы

Минимальный набор:

```text
+
-
*
/
^
!
%
```

`**` не поддерживается.

### 20.1. Процент

`%` — postfix-оператор:

\[
x\% = \frac{x}{100}.
\]

Это не modulo и не remainder.

```text
50%  = 0,5
50%% = 0,005
```

### 20.2. Приоритет операторов

От большего к меньшему:

```text
1. %
2. !
3. ^
4. unary + -
5. implicit multiplication
6. * /
7. + -
```

Следствия:

```text
-2^2   = -(2^2)
2^2^2  = 2^(2^2)
2^50%  = 2^(0,5)
5!%    = (0,05)!
```

`^` правоассоциативен.

Неявное умножение имеет более высокий приоритет, чем явные `*` и `/`.

```text
2/3π → 2/(3*π)
```

---

## 21. Неявное умножение и токенизация имён

Должны поддерживаться как минимум:

```text
2π
2(3+4)
(2+3)(4+5)
2sin(3)
πe
ecos(1)
```

Tokenizer использует registry известных функций и констант.

Правила:

1. точное зарегистрированное имя целиком имеет приоритет;
2. иначе выполняется разбиение на зарегистрированные имена;
3. используется longest known match;
4. если корректного разбиения нет — `UnknownIdentifierError`;
5. если остаются несколько равноприоритетных корректных разбиений — ошибка неоднозначности;
6. более длинное точное имя имеет приоритет над разбиением на несколько коротких.

Пример при известных `π`, `e`, `sin`, `cos`:

```text
πe       → π * e
πsin(2)  → π * sin(2)
ecos(1)  → e * cos(1)
```

Если зарегистрировано цельное имя `sinh`, то `sinh(1)` разбирается как `sinh`, а не как `sin * h`.

```text
sin(1)
```

эквивалентны.

## 25. Registry функций и констант

Grammar принадлежит ядру, но реализации функций и констант доступны через registry.

Registry не может добавлять новые операторы, виды скобок, правила приоритета, ассоциативности или синтаксические конструкции.

### 25.1. FunctionDefinition

Концептуально:

```ts
interface FunctionDefinition {
    name: string;
    arity: FunctionArity;
    supportsIteration: boolean;
    angleSensitive: boolean;

    evaluate(
        args: readonly RealValue[],
        context: EvaluationContext
    ): RealValue;
}
```

```ts
type FunctionArity =
    | { kind: "fixed"; count: number }
    | { kind: "range"; min: number; max: number };
```

Область определения и precision propagation остаются логикой реализации функции.

### 25.2. ConstantDefinition

```ts
interface ConstantDefinition {
    name: string;

    createValue(
        context: EvaluationContext
    ): RealValue;
}
```

Registry хранит способ создания значения, а не заранее вычисленную десятичную строку.

### 25.3. Итерации

Registry содержит одно определение функции. `sin[3](x)` не создаёт отдельную функцию `sin[3]`; iteration является частью AST/evaluator.

### 25.4. Логарифм

`log` имеет специальный синтаксис основания, поэтому parser строит специализированную структуру вызова/узел.

Registry не создаёт отдельные имена `log2`, `log3`, `log10` и т. п.

### 25.5. Встроенные определения

Константы:

```text
π
e
```

Функции:

```text
sin
cos
tan
exp
log
ln
abs
```

### 25.6. Кэширование констант

В пределах одного evaluation context допустимо совместно использовать один lazy-state константы несколькими узлами.

Evaluation graph поэтому может быть DAG, а не только деревом.

### 25.7. Конфликты

Запрещается регистрация имени, если оно уже занято функцией/константой, зарезервировано grammar или создаёт недопустимый tokenization conflict.

Встроенные сущности нельзя переопределять расширениями.

## 26. AST

AST неизменяем после построения.

Минимальные категории:

```text
NumberLiteralNode
ConstantNode
UnaryNode
BinaryNode
PostfixNode
FunctionCallNode
FunctionIterationNode
LogNode
```

AST описывает синтаксис, не хранит вычислительное состояние и не содержит типов сторонних библиотек.

## 27. Evaluation graph

Каждый вычислительный узел:

- знает зависимости;
- хранит собственный lazy-state;
- умеет запросить дополнительную точность детей;
- кэширует релевантные промежуточные данные;
- умеет продолжить вычисление;
- учитывает cancellation/resource budget;
- возвращает `Rational` или `LazyReal`.

Состояние графа живёт в RAM текущего сеанса и не является долговременным форматом данных.

---

## 28. Verified digits API

Публичный запрос точности:

```ts
interface PrecisionRequest {
    significantDigits: number;
}
```

Запрос означает: доказать первые `N` значащих десятичных цифр результата.

### 28.1. Структурированный результат

```ts
interface VerifiedNumber {
    sign: -1 | 0 | 1;

    digits: string;
    exponent10: bigint;
    verifiedDigits: number;

    valueExact: boolean;
    decimalTerminating: boolean;

    rounded: boolean;
    zeroKind?: "exact" | "rounded";
}
```

Для ненулевого числа первая цифра `digits` относится к разряду `10^exponent10`.

### 28.2. Exactness metadata

```text
1/8:
valueExact = true
decimalTerminating = true

1/3:
valueExact = true
decimalTerminating = false

sqrt(2):
valueExact = false
decimalTerminating = false
```

### 28.3. Verified prefix

`digits` содержит только цифры, доказанные текущим ball.

Если ball не позволяет доказать следующую цифру, ядро refine вычисление.

Увеличение точности не должно менять уже выданный verified prefix.

### 28.4. Scroll/refinement

UI запрашивает возрастающее количество значащих цифр:

```text
20
50
100
300
1000
...
```

Отдельный диапазонный API `getDigits(start,count)` на первом этапе не требуется.

---

## 29. CalculationHandle

Публичная вычислительная сущность является долгоживущей.

Концептуально:

```ts
interface CalculationHandle {
    refine(
        request: PrecisionRequest
    ): Promise<RefinementResult>;

    continue(): Promise<RefinementResult>;

    cancel(): void;
}
```

Семантика:

- один handle владеет одним evaluation graph;
- повторный refinement продолжает его состояние;
- timeout не уничтожает handle;
- отменённый handle продолжить нельзя.

---

## 30. RefinementResult

Концептуально:

```ts
type RefinementResult =
    | CompletedResult
    | PausedResult
    | CancelledResult
    | FailedResult;
```

### 30.1. Complete

Успешное обычное завершение запроса `N` означает, что ядро доказало не меньше `N` требуемых цифр, если exact finite representation не завершилось раньше естественным образом.

### 30.2. Paused

При soft timeout уже доказанные цифры не выбрасываются.

```ts
interface PausedResult {
    status: "paused";
    reason: "time-limit";
    requestedDigits: number;
    verifiedDigits: number;
    partial: VerifiedNumber | null;
}
```

### 30.3. Cancelled

Отмена является отдельным состоянием.

### 30.4. Failed

Математическая или внутренняя ошибка возвращается типизированно.

---

## 31. Отображение результата

Преобразование:

```text
VerifiedNumber
    ↓
formatter
    ↓
313,319591...
2,8284E136
```

не является обязанностью evaluator.

Formatter определяет обычную/научную запись, размещение десятичной запятой и визуальное представление, но не имеет права объявлять непроверенные цифры подтверждёнными.

---

## 32. История вычислений

В долговременной истории сохраняются:

- исходное выражение;
- текст отображённого результата;
- настройки, действовавшие при вычислении;
- необходимые идентификаторы/метаданные для повторного запуска.

Не сериализуются evaluation graph, partial sums, lazy-state, backend objects и вычислительные кэши.

### 32.1. Дополнительная точность старого результата

Если пользователь прокручивает старый результат дальше, использует его в новом вычислении или просит больше подтверждённых цифр, ядро пересчитывает исходное выражение с сохранёнными настройками.

### 32.2. Семантика Ans

`Ans` ссылается не на отображённую строку, а на исходное вычисление/запись истории:

```text
Ans
  ↓
history entry
  ↓
original expression + original settings
  ↓
re-evaluation to required precision
```

## 33. Настройки вычисления

Минимально:

```ts
interface EvaluationSettings {
    angleMode: "radians" | "degrees";
    factorialMode: "integer" | "gamma";
    maxCalculationTimeMs: number;
}
```

Изменение текущих настроек не меняет смысл уже сохранённой записи истории.

---

## 34. Soft time limit

`maxCalculationTimeMs` задаёт максимальную длительность одного непрерывного refinement-сеанса.

Например `5000` мс не означает, что всё вычисление обязано завершиться за 5 секунд. После примерно 5 секунд cooperative выполнения ядро должно вернуть управление UI.

### 34.1. Состояния

```text
idle
  ↓
running
 ├─→ completed
 ├─→ failed
 ├─→ cancelled
 └─→ paused
       ↓ continue
     running
```

`paused` из-за soft timeout не является ошибкой.

### 34.2. Continue

Каждый `continue` выдаёт новый полный временной бюджет того же размера. Лимит не увеличивается автоматически.

### 34.3. Сохранение состояния

При pause сохраняются evaluation graph, состояния lazy-узлов, partial sums/series state, достигнутые приближения, кэши и verified digits.

Продолжение не начинает вычисление заново.

---

## 35. Cooperative checkpoints

Долгие алгоритмы обязаны периодически проверять:

- elapsed time;
- cancellation signal;
- текущий resource budget.

Концептуально:

```ts
context.checkpoint();
```

Алгоритмы должны быть разбиты на достаточно мелкие resumable steps.

---

## 36. Отмена

Если пользователь изменяет выражение, старое вычисление может быть отменено.

```text
running → cancelled
paused  → cancelled
```

Продолжение отменённого `CalculationHandle` запрещено.

Поскольку кнопки `=` нет, изменение выражения создаёт новое вычисление после UI-level normalization/debounce.

---

## 37. Web Worker compatibility

Публичное вычислительное API должно позволять выполнять ядро вне UI thread.

```text
UI thread
   │
   │ refine / continue / cancel
   ▼
Calculation Worker
   │
   │ evaluation graph + lazy state
   │
   ├─ complete
   ├─ paused
   ├─ failed
   └─ cancelled
   ▼
UI thread
```

Web Worker не должен менять математические API или типы ядра.

---

## 38. Жёсткая аварийная защита

Помимо пользовательского soft time limit реализация может иметь внутренний hard watchdog и другие safety limits для защиты от зависшего алгоритма, ошибки реализации, аварийного расхода памяти или неисправного backend.

Hard limit не является пользовательской математической настройкой и может завершить вычисление без возможности продолжения.

`ResourceLimitError` относится к таким непродолжаемым ограничениям, а не к обычному soft timeout.

## 39. Ошибки

Ядро не использует `NaN`/`Infinity` как способ сообщить об ошибке.

Минимальные категории:

```text
CalcError
├─ SyntaxError
├─ UnknownIdentifierError
├─ AmbiguousIdentifierError
├─ DomainError
├─ DivisionByZeroError
├─ PrecisionError
├─ ResourceLimitError
├─ CancelledError
└─ InternalCalculationError
```

Ошибки должны быть машинно различимы.

Ошибки конфигурации registry оформляются отдельно от `CalcError`.

## 45. Фундаментальные инварианты

### I. Verified digits never regress

Если цифра была выдана как доказанная, обычное продолжение вычисления не должно впоследствии её изменить.

### II. True value stays inside the ball

Для каждого `LazyReal` истинное значение находится внутри возвращаемого ball.

### III. Exact rationals stay exact

Рациональные операции сохраняют точность, пока применяется реализованный exact path.

### IV. No hidden special values

Ошибки не маскируются под `NaN`, `Infinity`, `-0` и подобные значения.

### V. Precision is demand-driven

Узел вычисляет только необходимую дополнительную информацию.

### VI. Lazy state is local

Каждый вычислительный узел владеет собственным состоянием продолжения.

### VII. Library types do not leak

Сторонние numeric types не пересекают публичные границы ядра.

### VIII. History text is not the mathematical value

Отображённый текст результата не используется как источник точности для следующих вычислений.

### IX. Soft timeout preserves work

Обычный пользовательский timeout не уничтожает уже вычисленное состояние и verified digits.

### X. Cutoff error propagates

Погрешность, созданная precision cutoff, остаётся частью ball и учитывается всеми последующими операциями.

## 48. Критерий готовности математического ядра

Первый этап ядра считается готовым, когда:

1. выражение разбирается в AST согласно зафиксированной grammar;
2. точные рациональные выражения вычисляются без потери точности;
3. `LazyReal` умеет лениво уточняться;
4. binary arbitrary-precision backend поддерживает directed rounding;
5. ball arithmetic гарантирует границы ошибки;
6. основные функции и константы умеют выдавать доказанные цифры;
7. каждый узел сохраняет состояние продолжения;
8. precision propagation работает рекурсивно;
9. реализован precision cutoff;
10. различаются `ExactZero` и `RoundedZero`;
11. работают degree/radian modes;
12. domain errors определяются только после достаточного refinement;
