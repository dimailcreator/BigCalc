# ADR: `Ans` и публичная граница Core 1.0

## Статус

Архитектурный конфликт подтверждён на этапе 7. До решения нельзя строить history UI и составные выражения с `Ans` на подстановке отображаемого числа или исходного текста. Public Core API в рамках spike не меняется.

## Требуемая семантика

`AnsToken` хранит идентификатор конкретной записи истории. Значение записи определяется её исходным выражением и исходными математическими настройками; при новом запросе точности оно пересчитывается. Это следует из `CORE_SPEC.md` §32.1–32.2 и §33, `UI_SPEC.md` §6.3, §14.1 и §37.7. `APP_IMPLEMENTATION_PLAN.md` (этап 7, риск R2) требует доказать этот путь до реализации history UI.

## Проверка public API 1.0

Публичная поверхность `src/core/api.ts` содержит `createCalculationHandle(source, { settings })`, `formatVerifiedNumber` и служебные exports. Один handle получает **один** набор настроек. `CalculationOptions` не содержит ссылок на history entries, resolver, bindings или отдельных настроек для подвыражений. `VerifiedNumber` отдаёт конечный проверенный префикс, но не предоставляет рациональную дробь либо ball с погрешностью для дальнейшей Core-арифметики. `createCalculationHandle("Ans+1")` возвращает `UnknownIdentifierError`.

Проверка в `tests/app/ans-core-boundary.test.ts` использует только `@bigcalc/core`:

| Case                                                               | Наблюдение                                                                                                                                                                                                                 |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A, `1/3 → Ans+1`                                                   | Текстовая подстановка `(1/3)+1` в том же контексте сохраняет exact rational. Подстановка конечных цифр `1/3` даёт другой, terminating rational.                                                                            |
| B, `π → Ans*2`                                                     | `(π)*2` в том же контексте остаётся неточным lazy value и может уточняться. Подстановка конечного decimal prefix меняет математическое значение.                                                                           |
| C, `sin(30)` сохранён в градусах, новое выражение в радианах       | Сохранённый результат равен `0,5`. Подстановка `(sin(30))+1` под текущими radians вычисляет другое значение.                                                                                                               |
| D, `(-1/2)!` сохранён в Gamma mode, новое выражение в integer mode | Сохранённое вычисление успешно. Подстановка `((-1/2)!)+1` под текущим integer mode возвращает `DomainError`.                                                                                                               |
| E, дополнительная точность                                         | Новый handle для `(π)*2` может дать больше цифр при одинаковых настройках. Публичный API не может попросить вложенный старый результат уточниться под его собственными настройками и передать значение в новое вычисление. |

Простая подстановка исходного текста работает лишь в частном случае одинаковых настроек. Переписывание произвольного старого выражения под новые настройки потребовало бы отдельного математического parser/rewriter в application layer. Арифметика над конечными `VerifiedNumber` в приложении также не даёт доказанный путь: public DTO не содержит точного rational либо полного error bound. Оба подхода нарушают разделение Core и приложения; displayed decimal как значение `Ans` прямо запрещён.

В Core существует внутренний `createHistoryService` (`src/core/history/history.ts`) с ленивой переоценкой записи и сохранёнными настройками. Он экспортируется через `src/core/index.ts`, но **не** через замороженный `src/core/api.ts`; приложение не вправе импортировать его как обходную границу. Текущий внутренний `createCalculationHandleFromSourceWithAns` связывает одно имя `Ans` с одной записью. Редактор позволяет вставить несколько `AnsToken` с разными `historyEntryId`, поэтому даже прямой перенос этого интерфейса в public API не покрыл бы полный UI contract.

## Минимальные варианты решения

1. **Версионированное расширение публичного Core contract.** Передавать в Worker сериализуемое выражение и привязки каждого `AnsToken` к history entry ID. Core должен лениво вычислять каждую ссылку из исходного выражения с её исходными настройками, требовать дополнительную точность, сохранять strict bounds и exactness и участвовать в общем lifecycle/cancellation. Нужно явно определить обработку нескольких ссылок, вложенных ссылок, отсутствующих записей и ошибок. Внутренний history механизм показывает возможное направление реализации, но его API нельзя использовать из приложения без отдельного cross-boundary решения и public API audit.
2. **Сузить продуктовую семантику `Ans`.** Разрешить только отдельный просмотр/пересчёт старого результата и запретить его участие в новом выражении. Это требует явного изменения `CORE_SPEC.md` §32.2, `UI_SPEC.md` §6.3/§37.7 и плана; текущим требованиям вариант не соответствует.

До принятия решения риск R2 остаётся открытым. Этап 7 завершается формальным блокером по варианту 2 его Definition of Done; этапы, зависящие от составного `Ans`, не должны опираться на временную подстановку.
