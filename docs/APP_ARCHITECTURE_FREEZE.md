# App architecture baseline — Stage 26

Stage 26 freezes the first application contracts after the complete browser and Android flow. This is an internal compatibility baseline for bundled calculators and App components, not an npm package export. `CORE_SPEC.md`, `UI_SPEC.md`, and `DESIGN_SPEC.md` remain authoritative. Visual spacing, colors, and animation details are outside this freeze.

## Compatibility rules

- Keep the named contracts and their semantics stable for the next bundled calculator. Additive optional fields are allowed when old modules and stored documents keep working. Breaking changes require a documented decision, migration where persisted data is affected, and regression tests.
- Change the Worker DTO and both producer/consumer validation together. A transport failure remains distinct from a mathematical `CalcError`.
- Change a storage document version or module revision deliberately; loading an unknown version must not silently reinterpret it. Never persist Core graphs, Worker handles, or transient UI/session state.
- Keep `ExpressionModel` token boundaries and `NumberViewportModel` logical digit positions independent of DOM layout. Changes to mathematical meaning belong to Core.
- Add a bundled calculator in `src/app/modules/installedModules.ts` using `defineCalculatorModule`. Its view and state stay in the module. AppShell (`src/app/main.ts`) and `NavigationController` need no module-specific branch. The primary BigCalc remains the sole owner of History.

## Verification

The next-module criterion is exercised by `tests/app/modules/CalculatorModuleHost.test.ts` (registration, navigation, in-memory state, restart restoration) and `tests/app/module-framework.spec.js` (screen mounting under the existing shell). The full local gates are `npm run check` and `npm run check:app`. Android device behavior remains covered by the Stage 24 checklist; this architecture freeze adds no new device interaction.

## Calculator Modules Stage 6 extension direction

BMI established the existing native-input/module-local calculation path. Units additionally requires a replaceable mathematical keyboard target and generic module calculation/settings services, which the current runtime contract does not provide. The [Stage 6 ADR](decisions/ADR-APP-MODULE-INPUT-AND-CALCULATION-SERVICES.md) accepts additive, backward-compatible application extensions for Stages 7–9 with explicit regression obligations. Stage 6 documents this direction only: the frozen runtime contracts, Core API, Worker DTOs and persistence schema remain unchanged.

Stage 7 implements the replaceable keyboard target and press invalidation, preserving the legacy constructor, primary interaction and global controls. [Stage 7 verification](SHARED_KEYBOARD_STAGE7_VERIFICATION.md) records regression and Android evidence. Module runtime/service contracts, navigation/layout coordination, Worker transport and persistence remain at their existing baseline; Stages 8–9 are not implemented by this keyboard change.

Stage 8 implements the authorized additive module input boundary: optional input-only `inputKind` metadata, optional trailing `CalculatorModuleServices` on runtime/view creation and an application-owned `CalculatorModuleServiceScope` factory on Host. `services.inputs` registers math targets/native fields; modules do not receive scope lifecycle control. Host releases input routing before deactivation/disposal and cleans up construction failures. Legacy registrations and persisted documents remain compatible. `CalculatorInputCoordinator` owns selection, overlay/background suspension and focus safety; secondary shell tracks follow active math capability, while History remains primary-only. [Stage 8 verification](MODULE_INPUT_STAGE8_VERIFICATION.md) records unit/browser and physical Android BMI evidence. Core, Worker/editor contracts and persistence are unchanged; scoped calculations/current settings remain Stage 9 work.

Stage 9 implements optional `services.calculations` and `services.settings`. The higher-level owner service reuses the existing client/protocol and the one production Worker; module sessions gate pending work, immutable snapshots and late-response cleanup. Host activates scope before module hooks and releases sessions before deactivation/disposal; settings changes invalidate old work before notification. Primary controller gains an optional initial settings snapshot to avoid transient defaults, while primary/History/module IDs share an application allocator. History original settings/structured references are preserved. Core/version/grammar, Worker DTO/runtime, editor/persistence and BMI remain unchanged. [Stage 9 verification](MODULE_CALCULATION_STAGE9_VERIFICATION.md) records compatibility/concurrency and final gates. Stage 10 domain/Units production implementation is not included.

Stage 13 adds optional module presentation services (global inertia subscription and owner-scoped shared timeout actions) and optional ExpressionEditor text-to-token customization. The existing default editor parser is retained; Units uses its existing lossless source helper so unsupported Ans is rejected rather than filtered. The [Stage 13 ADR](ADR_MODULE_PRESENTATION_STAGE13.md) records the deficiencies and additive compatibility decision. The application routes its existing single dialog/navigation layer without module-ID branches, and Host cleanup retains its order. Core/version/semantics, Worker protocol, persistence schema, module state contract and keyboard layout are unchanged. [Stage 13 verification](UNITS_VIEW_STAGE13_VERIFICATION.md) records ownership and browser regression coverage. Units production registration and physical acceptance remain Stages 14–15.
