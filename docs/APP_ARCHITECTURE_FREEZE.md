# App architecture baseline — Stage 26

Stage 26 freezes the first application contracts after the complete browser and Android flow. This is an internal compatibility baseline for bundled calculators and App components, not an npm package export. `CORE_SPEC.md`, `UI_SPEC.md`, and `DESIGN_SPEC.md` remain authoritative. Visual spacing, colors, and animation details are outside this freeze.

## Compatibility rules

- Keep the named contracts and their semantics stable for the next bundled calculator. Additive optional fields are allowed when old modules and stored documents keep working. Breaking changes require a documented decision, migration where persisted data is affected, and regression tests.
- Change the Worker DTO and both producer/consumer validation together. A transport failure remains distinct from a mathematical `CalcError`.
- Change a storage document version or module revision deliberately; loading an unknown version must not silently reinterpret it. Never persist Core graphs, Worker handles, or transient UI/session state.
- Keep `ExpressionModel` token boundaries and `NumberViewportModel` logical digit positions independent of DOM layout. Changes to mathematical meaning belong to Core.
- Add a bundled calculator in `src/app/modules/installedModules.ts` using `defineCalculatorModule`. Its view and state stay in the module. AppShell (`src/app/main.ts`) and `NavigationController` need no module-specific branch. The primary BigCalc remains the sole owner of History.

## Calculator Modules Stage 6 extension direction

BMI established the existing native-input/module-local calculation path. At Stage 6, Units additionally required a replaceable mathematical keyboard target and generic module calculation/settings services, which the runtime contract did not yet provide. The [Stage 6 ADR](decisions/ADR-APP-MODULE-INPUT-AND-CALCULATION-SERVICES.md) accepted additive, backward-compatible application extensions for Stages 7–9 with explicit regression obligations. Stage 6 documented this direction only: the frozen runtime contracts, Core API, Worker DTOs and persistence schema remained unchanged. The keyboard target and scoped services now exist, as recorded below.

Stage 7 implements the replaceable keyboard target and press invalidation, preserving the legacy constructor, primary interaction and global controls. [Stage 7 verification](SHARED_KEYBOARD_STAGE7_VERIFICATION.md) records regression and Android evidence. At Stage 7, module runtime/service contracts, navigation/layout coordination, Worker transport and persistence remained at their existing baseline; Stages 8–9 were not implemented by that keyboard change.

Stage 8 implements the authorized additive module input boundary: optional input-only `inputKind` metadata, optional trailing `CalculatorModuleServices` on runtime/view creation and an application-owned `CalculatorModuleServiceScope` factory on Host. `services.inputs` registers math targets/native fields; modules do not receive scope lifecycle control. Host releases input routing before deactivation/disposal and cleans up construction failures. Legacy registrations and persisted documents remain compatible. `CalculatorInputCoordinator` owns selection, overlay/background suspension and focus safety; secondary shell tracks follow active math capability, while History remains primary-only. [Stage 8 verification](MODULE_INPUT_STAGE8_VERIFICATION.md) records unit/browser and physical Android BMI evidence. Core, Worker/editor contracts and persistence are unchanged; at Stage 8, scoped calculations/current settings were still Stage 9 work.

Stage 9 implements optional `services.calculations` and `services.settings`. The higher-level owner service reuses the existing client/protocol and the one production Worker; module sessions gate pending work, immutable snapshots and late-response cleanup. Host activates scope before module hooks and releases sessions before deactivation/disposal; settings changes invalidate old work before notification. Primary controller gains an optional initial settings snapshot to avoid transient defaults, while primary/History/module IDs share an application allocator. History original settings/structured references are preserved. Core/version/grammar, Worker DTO/runtime, editor/persistence and BMI remain unchanged. [Stage 9 verification](MODULE_CALCULATION_STAGE9_VERIFICATION.md) records compatibility/concurrency and final gates. Stage 9 did not include the Stage 10 domain or Units production implementation.

Stage 13 adds optional module presentation services (global inertia subscription and owner-scoped shared timeout actions) and optional ExpressionEditor text-to-token customization. The existing default editor parser is retained; Units uses its existing lossless source helper so unsupported Ans is rejected at the evaluation boundary rather than filtered from input. The [Stage 13 ADR](ADR_MODULE_PRESENTATION_STAGE13.md) records the deficiencies and additive compatibility decision. The application routes its existing single dialog/navigation layer without module-ID branches, and Host cleanup retains its order. Core/version/semantics, Worker protocol, persistence schema, module state contract and keyboard layout are unchanged. [Stage 13 verification](UNITS_VIEW_STAGE13_VERIFICATION.md) records ownership and browser regression coverage. At Stage 13, Units production registration and physical acceptance were scheduled for Stages 14–15; both have since been completed.

## Calculator Modules Stage 14 production registration

Stage 14 adds Units after BMI through `installedModules.ts`. It uses the completed Stage 13 view with the existing scoped inputs, calculations, authoritative settings and presentation services. Main, Host, Surface, navigation and shared persistence require no changes or module-ID branches. Primary, History and Units reuse the one Worker with independent session ownership; only primary owns History. Core/Worker/module contracts and persistence schemas remain unchanged.

The production browser suite covers independent primary/BMI/Units source state, exact Ans chaining, reload and result recomputation, global modes, shared timeout and keyboard/native focus, navigation, portrait layout and appearance. Evidence and final gate/build results are recorded in [Stage 14 verification](UNITS_INTEGRATION_STAGE14_VERIFICATION.md). At Stage 14, physical Android IME acceptance and new device automation were deferred to Stage 15; their completion is recorded below.

## Calculator Modules Stage 15 physical Android acceptance

Stage 15 confirms the generic native/math input coordination in production Units, the second secondary calculator after BMI. `NativeInputLayout` stabilizes numeric fonts and TopBar/button/wallpaper geometry during native IME viewport reduction, retaining live display-size scaling. Android consumes Back for native IME; the application then closes the top overlay first. Primary BigCalc never dismisses its shared keyboard by Back: it uses the navigation stack, or exits at root. A secondary calculator dismisses an open shared math keyboard before subsequent Back uses navigation; source/session survive until normal deactivation. Shell/navigation contain no Units-specific branches.

Primary, History and Units use one shared Worker with independent calculation sessions; BMI remains module-local. Persistence stores only original Units source strings, and a fresh restart creates new sessions and recomputes results. Physical Android acceptance on the reported Samsung device covers mixed input, geometry, Back, switching, appearances and restart. The [final Stage 15 verification report](UNITS_CALCULATOR_VERIFICATION.md) identifies production commit `7594cc26305dcdba0b379a6e7f2060aa60d56c27`, distinguishes initial closure and Primary Back follow-up, and records the later full verification on `968d090` (first browser FAIL, diagnostic failures, successful full rerun). Test-only commit `1eee509` then stabilizes the Units resize assertion by awaiting held/release state; targeted plus 10/10 repeats and new full Core/App gates passed on its exact test tree before commit. The formal final-tree gap is closed and the observed test instability corrected; subsequent edits are documentation only. Physical acceptance and APK builds were not repeated by these verification/test follow-ups. These results extend the historical baseline without defining new contracts or changing production code.
