# Calculator modules

`src/app/modules/CalculatorModule.ts` defines the module contract. The application owns the top bar, navigation stack, drawer, and keyboard layout. A module owns its fields, calculation behavior, output, errors, and calculation lifecycle inside its view. Only the primary BigCalc screen has history.

To bundle another calculator, create it with `defineCalculatorModule(...)` and add the registration to `src/app/modules/installedModules.ts`. `CalculatorModuleHost` supplies the drawer and navigation registrations; `CalculatorModuleSurface` mounts the module view. AppShell and `NavigationController` need no module-specific branches.

`fields` declares input and output IDs, labels, and optional descriptions. Input descriptors can optionally declare `inputKind: "math-expression" | "text"`; output descriptors cannot. Metadata alone does not activate an editor. If a view renders a description label, it follows the label → description dialog interaction in `UI_SPEC.md`. The module contract has no keyboard layout setting.

State lives in memory while the app runs. A module with a `persistence` declaration also implements `restoreState` and `serializePersistentState`. The host loads that declaration when it creates the module, saves it before deactivation, and flushes it on page hide. The declaration controls which JSON data survives restart. Worker handles, live calculation graphs, and other runtime objects must stay out of the persistent DTO.

`tests/app/modules/CalculatorModuleHost.test.ts` registers a test calculator, switches to it through the existing navigation controller, and verifies state retention and restart restoration. `tests/app/module-framework.spec.js` checks that its screen mounts without changing the main shell.

## Scoped input services — Stage 8

`createRuntime(repository, services?)` and `createView(state, services?)` accept an optional trailing application services context. Existing callers and module hooks remain compatible. The production Host supplies an owner scope to every runtime; modules receive optional `inputs`, `settings` and `calculations` services, not scope management.

The input service exposes `registerMath(target)` and `registerText(input)`. Both return an idempotent registration with `activate()`, `deactivate()` and `dispose()`. A mathematical target uses the Stage 7 `CalculatorKeyboardTarget`; its registration also exposes `submit()` for the editor's physical Enter callback, gated to the current target. The keyboard's `=` invokes that same target action. A module owns its editor, clear/submit behavior and native fields, while App owns the one keyboard and its global controls.

Register fields while creating the view. The first math registration becomes the default selection without autofocus. Focus/explicit activation selects a field; native focus disables math routing and permits IME. Math activation blurs native text and suppresses Android IME through `inputMode="none"`. Unregistered legacy native fields remain supported, including BMI. Dispose registrations when removing fields; Host releases the entire input scope before runtime deactivation/disposal and cleans up scopes if construction fails.

The coordinator remembers each runtime's selected field across module navigation and overlays. Drawer/Settings/About, background, module switching and pagehide suspend input routing and stop held actions. Resume does not focus hidden, inert, detached or disposed editors or steal native Settings focus. Only the still-selected active math field may regain its background focus; native fields are not automatically focused. Focus/selection/registration are runtime data and are not persisted.

Secondary math content scrolls in the bounded region above the bottom keyboard track. Secondary native/no-target content fills the space below TopBar, with the keyboard hidden. History is primary-only. `NativeInputLayout` retains TopBar/wallpaper geometry until the actual viewport restores, including a transition from native text to math while Android is closing IME. Primary overlay geometry is preserved behind its inert layer with routing suspended.

The synthetic math/text calculator is installed only in `tests/app/fixtures/module-input.js`. It exercises both layouts, routing, lifecycle and IME resize; it is absent from production registrations and builds. Evidence: [Stage 8 verification](MODULE_INPUT_STAGE8_VERIFICATION.md).

## Scoped calculation/settings services — Stage 9

`ModuleCalculationService` wraps the existing shared `CalculationClient`/Worker. The application supplies its authoritative evaluation snapshot and updates it from primary controller emissions, covering Settings and keyboard controls. Modules can only `settings.read()` and `settings.subscribe(listener)`; read/notification snapshots contain exactly `angleMode`, `factorialMode`, `maxCalculationTimeMs` and are immutable. The existing non-negative finite timeout contract (including zero/fractional milliseconds) is retained. Equal settings and appearance/inertia changes do not notify or invalidate sessions.

`calculations.create(source, settings?)` returns a runtime-only session; omitted settings use the current snapshot, explicit settings are copied. `ready` resolves `{ok:true}` or `{ok:false,error:CalcErrorDto}`. `refine(significantDigits)` and `continue()` return existing `RefinementResultDto`; a pause retains the same Worker handle. Consumers freeze by withholding further requests, not by calling irreversible `cancel()`. `cancel()` and `dispose()` are idempotent terminal actions. Mathematical errors remain DTOs; transport failures reject with `CalculationTransportError`. Only one refinement/continuation may be pending per session, including during creation. Sessions expose no Worker handle, transport termination or another owner's sessions.

Start work from the module's activation hook or active view events, not during inactive view construction. Host activates the service scope before the module hook, and closes its sessions before deactivation/disposal. Return creates new work from source. Settings change closes all old module sessions before notifying listeners; the module controller owns source revisions and recomputation. Dispose the old session on source replacement. Subscriptions remain readable across deactivation and are removed on owner disposal; inactive listeners may update local state but must defer calculations until activation. Preserve only declared source DTOs in persistence.

Primary BigCalc, History refiners and module sessions share the application-realm session/request allocator, eliminating controller-local counters/UUID namespaces. Primary and History keep their existing transport/lifecycle behavior; History replay still uses the original expression/settings, not the current settings service. App cleanup releases owners/controllers/History before terminating its one Worker. Modules cannot terminate it. The synthetic calculation owner exists only in `tests/app/fixtures/module-calculation.js` and uses the actual Worker/Core boundary without importing Core. Evidence: [Stage 9 verification](MODULE_CALCULATION_STAGE9_VERIFICATION.md).

## Bundled BMI calculator

The production drawer contains BigCalc first, **ИМТ** (`bmi`) second and **Единицы** (`units`) third. BMI has native height (cm) and weight (kg) inputs and calculates immediately within its own module; it does not use Core, Worker, or the primary calculation lifecycle. It has no history, custom keyboard, or calculate button.

The module accepts positive finite decimal input with comma or dot. It displays at most two decimal places with a comma and no trailing zeroes. Category is derived from the unrounded BMI: `100 cm / 29,996 kg` displays `30` but remains `Избыточная масса`. The normative category table and input states are in [UI_SPEC §43.5](../UI_SPEC.md#435-имт--первый-secondary-bundled-calculator).

Persistence stores only `heightText` and `weightText` in `bigcalc.app.calculator-state.v1`, module revision 1. Outputs are recomputed after restore. Switching retains both calculators' state; a fresh app may start on BigCalc. BMI inherits global theme/palette, including Liquid Glass; `displaySize` does not change its form typography.

Run `npm run test:android:bmi` with a connected physical Android device and the current debug APK installed. Use `ANDROID_SERIAL` to select a device and `ANDROID_HOME` to select the SDK (otherwise `.android-sdk` is used). `-- --with-regressions` also runs existing Android smoke, lifecycle, and Stage 34 acceptance inside the same storage snapshot guard. Input uses native ADB taps/text events; CDP observes the WebView and selects existing input text. Entry settings/history/module data are restored before bootstrap and checked even after failures. Evidence is written to `.release-test/bmi/android/`.

Implementation and acceptance evidence: [BMI verification report](BMI_CALCULATOR_VERIFICATION.md), [calculator modules plan](../CALCULATOR_MODULES_IMPLEMENTATION_PLAN.md).

Android IME acceptance also compares shared TopBar and wallpaper geometry before/open/closed and reaches the result with native module swipes in four appearances. Shared Android layout retains chrome geometry during a native input's viewport reduction; the module surface still resizes and scrolls. Browser regression covers release on viewport restoration/width change and ordinary responsive resizing.

## Bundled Units calculator: Единицы

Calculator Modules Stage 6 specifies `units` / **Единицы**; Stage 14 installs it after BigCalc and BMI through `installedModules.ts`. [UI_SPEC §§43.6/44.2](../UI_SPEC.md) defines source/input/conversion/persistence behavior; [DESIGN_SPEC §50](../DESIGN_SPEC.md) defines portrait layout. Source state is three strings: `valueSource`, `fromUnitText`, `toUnitText`, with defaults `1`, `км/ч`, `м/с`; revision 1 uses the existing module-state repository/document. Parsed units, compiled source, sessions, results, focus and selection are derived/runtime data and never persisted.

The value field uses the existing mathematical editor and the one application keyboard (`math-expression`, Android IME suppressed). Two native unit fields use `text` input/IME with the application keyboard hidden. History remains primary-only; Units rejects `Ans`/history-reference insertion, including paste, and `=` does not replace its source or create primary history. Result uses `VerifiedNumberDto` / `NumberViewport`, not prototype decimal rounding; global display size applies to mathematical displays.

Unit parsing/dimensions/prefixes stay module-local. Conversion compiles exact rational/symbolic scale/offset expressions into ordinary Core source and calculates through the existing shared Worker. Signed integer powers and the seven SI dimensions are explicit; affine temperature expressions are standalone. Names/aliases/unit AST never enter Core and JavaScript `number` is not an authoritative factor. All 63 prototype entries and 20 prefixes, resolution collisions and quarantined entries are recorded in the [registry audit](UNITS_REGISTRY_AUDIT.md). Quarantined/custom or uncertain entries need explicit decisions before inclusion.

Stage 7 provides the replaceable mathematical target through `CalculatorKeyboardTarget`, `setTarget`/`clearTarget` and disposal. Stage 8 supplies scoped inputs and two secondary layouts; Stage 9 supplies scoped calculations/current settings over the shared Worker, as described above. Primary BigCalc and Units register independent production math targets; global modes/expansion are separate and target changes invalidate held presses/stop backspace repeat. The legacy constructor remains compatible. The [Stage 6 ADR](decisions/ADR-APP-MODULE-INPUT-AND-CALCULATION-SERVICES.md) governs these extensions. Existing BMI and legacy module registrations remain backward compatible; module-ID shell branches, private Core imports and module-owned keyboards/Workers are excluded.

## Pure Units domain — Stage 10

`src/app/modules/units/` contains a pure TypeScript domain with no App runtime, DOM, Worker, Core imports/execution or persistence. It is not imported by the production entrypoint. `UnitRegistryEntries` implements exactly the Stage 6 audit's 59 accepted units and 20 decimal prefixes. Four quarantined entries and the newer/binary prefixes remain excluded. Conventional definitions carry descriptions: Julian year/light-year, international length, avoirdupois mass, thermochemical calorie and metric tonne.

`UnitRegistry.resolve(token, range?)` uses NFC direct symbol → normalized name → longest valid single prefix. Symbols and prefix symbols retain case/Latin-Cyrillic identity; micro variants are explicit aliases. Name normalization folds case/ё and internal hyphens/underscores, preserves explicit punctuation, and never removes expression whitespace/operators. Spelled-out prefixes preserve the remainder's symbol case. Unique IDs/normalized alias collisions are validated at construction; equal aliases for one identity are accepted, different identities never silently overwrite. Same-tier prefix ambiguity raises a typed error. Prefixes are forbidden for kg/kcal, K and affine temperatures.

`parseUnitExpression(source, registry?)` returns immutable `{source, syntax, value}`. Syntax retains original UTF-16 ranges and unit/prefix identities; the source is unchanged. Atom/group → one lexical signed integer power → product/quotient left-to-right; only whitespace supplies implicit multiplication. All seven dimensions and signed exponents use `bigint`, with no overflow/coercion through `number`. Linear values carry exact scale nodes and a standalone ID only for an unprefixed atom with optional groups. Compounds/powers clear that marker, preserving the distinction between `K` and `K*m/m` for the later affine conversion compiler. Affine expressions allow only a standalone atom with optional groups; product, quotient, every power and prefixes are rejected.

`UnitScale` has only canonical bigint rationals, `π`, product, quotient and integer-power nodes. `compileUnitScale` serializes this trusted representation to parenthesized mathematical source without evaluating it or interpolating raw unit text. Large powers stay symbolic. An affine transform explicitly means `base = (input + inputOffset) * scale`, including zero-offset Rankine. Parsing returns typed `UnitDomainError` codes/ranges, separate from `UnitRegistryConfigurationError`, Core math and transport failures. These six Stage 10 domain files create no calculation sessions or results; the Stage 11 controller below supplies execution through existing services.

## Units compiler and calculation controller — Stage 11

`compileUnitConversion(value, parsedFrom, parsedTo)` preserves the original mathematical source and compiles trusted exact scales/offsets into ordinary parenthesized Core source. It accepts a source string or the editor's `EvaluationRepresentation`; structured History references and raw reserved `Ans` tokens are rejected. Dimension mismatch and affine counterpart errors occur before Worker creation. Affine conversions require both units to be standalone temperature atoms/groups; `K*m/m` and `K^1` are not standalone counterparts. Negative temperature values have ordinary mathematical semantics, without an added physical-range restriction.

The compiler checks delimiter containment only, not mathematical grammar. Unbalanced values are sent unchanged to Core creation with `requiresValueSyntaxCheck`; a syntax failure stays a Core diagnostic and no refinement runs. This prevents conversion wrappers from accidentally repairing an input such as `1)*2+(3`. An unexpected successful creation in that branch is a protocol failure, never a conversion result. Balanced value syntax/unknown identifiers/domain/resource failures are also handled by Core. `factorSource` contains exact source for linear metadata, or null for affine; it is not a displayed numeric factor. A view choosing to show a numeric factor must use a separate verified session.

`UnitsCalculationController(calculations, settings, onChange, options)` consumes only Stage 9 module services. Options specify `initialSignificantDigits`, optional debounce and initial source strings (defaults `1`, `км/ч`, `м/с`). Construct it while creating a view, activate it from the module hook after Host activation, deactivate it from the module hook, and dispose it with the view. `setSources` snapshots all three strings and the editor representation, immediately clears obsolete result/diagnostics, increments generation and cancels/disposes previous work. Settings subscription applies the same lifecycle to changes of angle/factorial/timeout. Inactive controllers defer work; returning recomputes retained sources. Disposal unsubscribes and releases the session. No History, global navigation, persistence or Worker ownership is exposed.

State separates unit errors (with field), Core DTO errors and transport errors; it exposes a verified number, immutable source/settings snapshots, compilation, phase and timeout-dialog flag. Empty sources and incomplete unit syntax are neutral during live edits. Mathematical syntax is interpreted only by Core; live syntax failures remain neutral until explicit submit, while other Core failures retain their category. Every async completion, rejection, ready acknowledgement and continuation is gated by current session identity/generation/activation.

Supply `initialViewportPrecisionDemand(resultViewport.availableSlots)` as the initial demand. Feed current `state.result` into the existing `NumberViewport` and route its precision callback to `requestMoreDigits`; extra requests coalesce on the same handle. No extra work runs for already verified digits or finite exact/rounded results. Additional-digit timeouts continue automatically and partial results cannot lower the verified digit count. `submit()` confirms a complete source, continues paused/frozen work, marks a pending initial operation explicit, or retries failures. The first live timeout is hidden, a repeat explicit timeout opens the interaction, and `cancelTimeout()` freezes without cancelling the handle. `continueCalculation()` resumes it. New source/settings or deactivation releases frozen work. Future view/navigation code owns the shared timeout interaction; Stage 11 adds no production view.

`tests/app/fixtures/units-calculation.js` wires the controller to the actual shared Worker, Host hooks, primary controller/History and `NumberViewport` only for tests. Production registrations remain BigCalc and BMI. [Stage 11 verification](UNITS_CALCULATION_STAGE11_VERIFICATION.md) records conversions, lifecycle/race tests and gate results.

## Units source state and definition — Stage 12

`UnitsState` and `PersistedUnitsStateV1` contain exactly `valueSource`, `fromUnitText`, `toUnitText`. `createUnitsState()` returns a fresh immutable source snapshot with defaults `1`, `км/ч`, `м/с`. `serializeUnitsState` selects those three strings explicitly; whitespace, casing, empty/incomplete/invalid source are retained without coercion or mathematical/unit validation. `unitsStatePersistence` declares `moduleId = units`, `revision = 1`, using the existing calculator-state document and application schema 1. Malformed DTOs return null for the repository/Host default fallback; foreign derived properties are ignored. Existing BMI/unknown module/future revision records are retained, and a future application document cannot be overwritten.

`unitsCalculatorDefinition` declares `units` / `Единицы` and four fields: `value` / Значение / math-expression, `fromUnit` / Из единиц / text, `toUnit` / В единицы / text, and `result` / Результат / output. It supplies state/persistence/restore through the generic module contract. `unitsCalculatorModule` is installed after BMI on Stage 14. Stage 12 left `createView` unset; Stage 13 attaches `UnitsCalculatorView` and controller lifecycle hooks before Stage 14 installation. Persistence tests retain their observer views by spreading the production definition. No placeholder screen or module-specific Host/shell branch is needed.

`createUnitsExpression(valueSource)` reconstructs a fresh `ExpressionModel` through `parseEditorText` and existing token constructors. Known names retain atomic boundaries and original casing. Persistence is source restoration, not filtered clipboard insertion: unsupported text/whitespace is retained as syntax characters for Core diagnostics, and raw `Ans` stays visible/atomic with no History identity. The display/evaluation source equals the original string, including invalid source; nothing is replaced with saved result digits. This helper recognizes editor tokens only and introduces no mathematical parser. Cursor/selection start from fresh model defaults and are never restored from foreign saved properties.

At view construction, derive the editor using `createUnitsExpression(state.get().valueSource)` and construct a new Stage 11 controller with `initialSources: state.get()` and the current module services; activation then recomputes parsed units/compiled source/verified result. Keep editor models, parsed units, settings snapshots, controllers, errors/results, viewport position, focus/selection and session/Worker IDs outside `UnitsState`. Save only current original source strings through the state handle. Host retains source state through switching and recreates derived state on restart. `tests/app/fixtures/units-state.js` demonstrates this lifecycle with observer views, real localStorage and shared Worker; it is not the production Units view. Evidence: [Stage 12 verification](UNITS_STATE_STAGE12_VERIFICATION.md).

## Units production view and generic presentation service (Stage 13)

`UnitsCalculatorView` requires input/calculation/settings/presentation services. Its real ExpressionEditor suppresses software IME and uses optional `parseText` to call the existing source-preserving reconstruction helper. All editor user text paths use this callback; the primary editor's default parser and atomic editing behavior are unchanged. Typed/pasted/composed/replacement-input Ans and structured History tokens reach the compiler's explicit rejection. The module creates no keyboard or Worker.

The view registers one math target and two native text inputs. All edits immediately invalidate obsolete output; swap, examples and form reset each commit one source snapshot. Keyboard AC clears only the mathematical target; screen Очистить has the distinct accessible name Очистить форму and resets to `1` / empty unit strings. Chips replace selection in the last focused unit input, defaulting to fromUnit, and leave focus on the reference control rather than opening IME. Native text/composition/caret remain browser-owned.

NumberViewport receives only the current verified result and requests further digits on the same controller. Accessible context includes the target and source conversion; a separate status announces the initial result once per generation, rather than each refinement. Copy serializes verified presentation text plus the target using the existing formatter; invalid/stale output disables it. Feedback expires without changing button width, and asynchronous completion after source change/deactivation is ignored. Five distinct error zones cover value/Core, fromUnit, toUnit, conversion and transport. No numeric factor is shown.

`ModulePresentationService` wraps the existing scope without module identity checks. Its optional `presentation` service exposes `readInertia`, `subscribeInertia`, and `setTimeout(actions | null)`. Only the active owner can publish timeout callbacks; leaving/disposal clears that interaction before inner cleanup. `main.ts` routes the existing single TimeoutDialog and navigation layer to the active module or primary controller. Evaluation settings, Worker protocol, persistence and installed modules are unchanged. The minimal additive boundaries and deficiency are documented in [Stage 13 ADR](ADR_MODULE_PRESENTATION_STAGE13.md).

Units CSS inherits numeric display tokens and semantic surfaces/focus/errors/glass tokens. Global displaySize scales editor/result only; native fields, labels and catalog controls retain stable sizes. The bounded module surface and NativeInputLayout remain generic. [Stage 13 verification](UNITS_VIEW_STAGE13_VERIFICATION.md) records portrait/browser coverage; Stage 14 production registration and Stage 15 physical Android acceptance are separate.
